# IS14 Economy Editor

Браузерный редактор ассортимента платных автоматов IS14. Данные берутся из настоящего загрузчика прототипов; для работы дизайнеров игровой сервер не нужен.

## Быстрый запуск

Нужен .NET SDK 10, как для игры. Выполняйте команды из корня репозитория.

```powershell
# Один раз, затем после изменений игровых предметов, ассортимента или локализации.
powershell -ExecutionPolicy Bypass -File Tools/EconomyEditor/scripts/export_catalog.ps1

# Запуск редактора.
dotnet run --project Tools/EconomyEditor/EconomyEditor.csproj
```

Откройте **http://127.0.0.1:5187**. На Linux выгрузка запускается командой:

```sh
sh Tools/EconomyEditor/scripts/export_catalog.sh
```

Первичная выгрузка собирает игровой загрузчик и поднимает его тестовое окружение без подключения к вашему серверу. Это может занять несколько минут. Отдельная папка `bin/EconomyCatalogExporter` позволяет оставить игровые процессы работающими. Если здесь уже запущена другая выгрузка, дождитесь её завершения.

## Работа дизайнера

1. Выберите автомат слева. Список включает все конкретные прототипы с `IS14VendingMachine`.
2. Найдите предмет по русскому названию или ID; нажмите на него либо перетащите в ассортимент. Повторные товары внутри вкладки не создаются.
3. Задайте цену и начальный запас. «Цены ±%» меняет цены всей выбранной вкладки.
4. Настройте вкладки: русское и английское название, доступы. Достаточно любого выбранного доступа; пустой список означает свободный доступ. Контрабанда редактируется отдельно.
5. В параметрах автомата доступны счёт выручки, налог и копирование наполнения другого автомата.
6. Сохраните проект. Общие проекты доступны другим людям на этом же сервере редактора. «Копия» создаёт независимый вариант. История позволяет открыть старую версию как новый проект.
7. Скачайте JSON для обмена или ZIP «Экспорт для игры» для применения в репозиторий.

Проект содержит весь набор автоматов. Янтарная точка отмечает отличие от снимка каталога. Начальные цены и запасы новых позиций — **100 кредитов и 5 штук**, это редактируемые значения, а не рассчитанные рекомендации баланса.

Незавершённые изменения дополнительно сохраняются в localStorage браузера. Не используйте его как единственную резервную копию: сохраните проект на сервере либо скачайте JSON. Одновременное сохранение старой версии проекта возвращает конфликт, а не перезаписывает чужую работу. При конфликте скачайте свой JSON/создайте копию, затем откройте актуальный общий проект.

## Каталог и картинки

Экспортёр является режимом `Content.YAMLLinter --export-economy-catalog <directory>`. Он использует:

- серверные прототипы для предметов, ассортимента, доступов и счетов;
- **клиентские** разрешённые маппинги для Sprite/Icon: сервер игнорирует часть их полей и не разрешает такое наследование полностью;
- локализацию `ru-RU` для названий и описаний и `en-US` для английских названий вкладок;
- только производственные прототипы, без тестовых сущностей.

Снимок содержит `catalog.json` и нужные PNG/RSI-метаданные в `textures/`. Это готовый переносимый пакет: редактору не нужен доступ к остальному репозиторию. Версия — хеш содержимого каталога и используемых текстур, отдельно записаны commit и дата экспорта. `missing-textures.txt` перечисляет отсутствующие ссылки исходного проекта.

Иконки в браузере — статические первые кадры разрешённых слоёв Sprite/Icon с цветом, смещением, масштабом и вращением. Это **не полная симуляция** игровых визуализаторов: процедурные эффекты, шейдеры и содержимое ёмкостей могут отличаться. При отсутствии статического изображения показывается ромб, но предмет остаётся доступен по ID.

После обновления снимка перезапустите редактор. Старые проекты сохраняются: несовпадающая версия каталога помечается, удалённые предметы можно оставить в черновике, но экспорт их отклонит.

## Применение в игру

Экспорт **не изменяет работающий раунд**. Распакуйте ZIP. `components/*.yml` — фрагменты компонентов, не самостоятельные прототипы: их нельзя просто положить в `Resources/Prototypes`.

Для проверки и применения нужен Python с PyYAML (`python -m pip install PyYAML`). Из корня игрового репозитория:

```sh
# Только показать diff; никакие файлы не меняются.
python Tools/EconomyEditor/scripts/apply_project.py path/to/unpacked/project.json

# Применить рассмотренные изменения.
python Tools/EconomyEditor/scripts/apply_project.py path/to/unpacked/project.json --apply
```

Импортёр проверяет ID предметов, автоматов, доступов и счетов, цены, запасы, повторы и конфликтующие переводы. Обновляет только `revenueAccount`, `taxPercent`, `tabs`, `contrabandInventory` в собственном компоненте `IS14VendingMachine`, сохраняет остальные компоненты и YAML-теги. Комментарии внутри переписанного компонента могут быть потеряны; комментарии и текст остальных компонентов сохраняются. Если у производного автомата нет собственного компонента, импортёр явно сообщит об этом.

Русские/английские названия вкладок обновляются в существующих Fluent-записях. Новые ключи попадают в `Resources/Locale/<locale>/_IS14/economy-editor.ftl`. Русские названия и описания в YAML не добавляются. После применения обычный diff и проверки проекта остаются частью работы с игровым репозиторием.

## Настройки и размещение

```powershell
$env:EDITOR_TOKEN = 'your-long-shared-access-key'
dotnet run --project Tools/EconomyEditor/EconomyEditor.csproj -- --urls http://127.0.0.1:5187 --catalog C:/snapshots/is14 --data C:/data/economy-editor
```

- По умолчанию приложение слушает только `127.0.0.1:5187`.
- `--catalog`: папка снимка; по умолчанию `Tools/EconomyEditor/data/catalog`.
- `--data`: папка SQLite; по умолчанию `Tools/EconomyEditor/data/projects`.
- `EDITOR_TOKEN`: общий ключ для API. Интерфейс запросит его при открытии, ключ хранится только в sessionStorage текущей вкладки/сеанса браузера. Если ключ не задан, локальная версия не требует входа.
- Статические изображения снимка доступны без ключа; проекты и API защищены ключом. Поле «Автор» — подпись, а не подтверждённая личность. Индивидуальных учётных записей, приглашений и ролей в первой версии нет.

Для доступа из интернета используйте HTTPS через обратный прокси и непустой `EDITOR_TOKEN`. Не меняйте адрес на публичный без настройки доступа. Прокси должен сохранять исходный `Host`; сервер принимает браузерные изменения только с того же origin. Для TLS-прокси настройте `ASPNETCORE_FORWARDEDHEADERS_ENABLED=true` и ограничьте доверие к прокси на уровне сети.

Контейнерная сборка из корня репозитория **после выгрузки каталога**:

```sh
docker build -f Tools/EconomyEditor/Dockerfile -t is14-economy-editor .
docker run --rm -p 127.0.0.1:5187:8080 -e EDITOR_TOKEN=your-access-key -v economy-projects:/data is14-economy-editor
```

Либо `EDITOR_TOKEN=your-access-key docker compose -f Tools/EconomyEditor/compose.yml up -d --build`.

Образ содержит снимок каталога, база хранится в отдельном volume. Обновление образа не заменяет проекты. Для резервной копии SQLite используйте штатный SQLite backup API или остановите сервис и сохраните всю папку данных (включая WAL/SHM при их наличии). Файлы снимка, база и результаты сборки игнорируются Git.

## Проверки

```sh
dotnet build Tools/EconomyEditor/EconomyEditor.csproj
node --check Tools/EconomyEditor/wwwroot/app.js
python -m unittest discover -s Tools/EconomyEditor/tests -p test_apply_project.py -v

# Запускайте HTTP-тесты на отдельной тестовой базе: они создают проекты.
dotnet run --project Tools/EconomyEditor/EconomyEditor.csproj -- --data /tmp/is14-editor-tests
python -m unittest discover -s Tools/EconomyEditor/tests -p test_api.py -v
```

Для HTTP-тестов поддерживаются `EDITOR_URL` и `EDITOR_TEST_TOKEN`. Перед публичным размещением отдельно проверьте доступ, резервное копирование, TLS и лимит размера запросов на вашем хостинге.

## Автодеплой при Publish

Оба существующих workflow (`Publish` и `Publish Testing`) автоматически собирают свежий снимок и обновляют соответствующий экземпляр редактора. Деплой происходит **на Docker daemon того же self-hosted runner, который выполняет этот Publish**, не на Robust.CDN и не на GitHub Pages. Если runners несколько, назначьте нужной машине уникальный label и задайте его в Variable `ECONOMY_EDITOR_RUNNER`: база и контейнеры остаются на конкретной машине. Удалённого SSH-деплоя в этой схеме нет.

Однократная настройка:

1. Установите Docker Engine на self-hosted runner и дайте пользователю runner доступ к `docker info`, `docker build` и `docker run`.
2. В GitHub → **Settings → Secrets and variables → Actions → Secrets** добавьте `ECONOMY_EDITOR_TOKEN` — общий ключ входа в рабочий редактор.
3. При желании добавьте `ECONOMY_EDITOR_TESTING_TOKEN` для тестового экземпляра; иначе он использует тот же ключ, что рабочий.
4. Для доступа по домену направьте обратный прокси на нужный порт этого runner, сохраните исходный Host и используйте HTTPS.

Без Docker или непустого ключа workflow завершается с понятной ошибкой на предварительной проверке, до сборки и публикации игры. Значение ключа не передаётся в аргументах команд или образе: Docker получает его из окружения шага запуска.

| Workflow | Контейнер | Адрес по умолчанию | Постоянный volume |
| --- | --- | --- | --- |
| Publish | `is14-economy-editor-production` | `127.0.0.1:5187` | `is14-economy-editor-production-projects` |
| Publish Testing | `is14-economy-editor-testing` | `127.0.0.1:5188` | `is14-economy-editor-testing-projects` |

Необязательные GitHub **Variables**:

- `ECONOMY_EDITOR_RUNNER` — уникальный label self-hosted runner для обоих workflow; по умолчанию используется прежний `self-hosted`. В пуле из нескольких машин закрепление обязательно для сохранения одного места размещения базы.
- `ECONOMY_EDITOR_BIND_ADDRESS` — IPv4-адрес привязки, по умолчанию `127.0.0.1`.
- `ECONOMY_EDITOR_PORT` — рабочий порт, по умолчанию `5187`.
- `ECONOMY_EDITOR_TESTING_PORT` — тестовый порт, по умолчанию `5188`; он должен отличаться от рабочего на одной машине.

Каждая публикация выполняет следующую цепочку:

1. Выгружает каталог в **новую временную папку**. Снимок из локального `data/catalog` или прошлого запуска не используется.
2. Собирает опубликованный веб-сервис и запускает проверки импортёра, логики деплоя и HTTP API. Тестовый сервер слушает случайный свободный локальный порт и использует отдельную временную SQLite-базу, поэтому не обращается к рабочим проектам.
3. Проверяет совпадение commit снимка с `GITHUB_SHA`, собирает Docker-образ с приложением и каталогом, помечает его точным SHA и версией снимка. Для каждого канала свой tag.
4. Сохраняет `deployment.json` как артефакт workflow: commit игры и движка, версия/дата снимка, число сущностей и автоматов, имя образа.
5. После успешного шага **Publish version** запускает проверочный контейнер на случайном loopback-порту. Проверяет `/health`, включая commit, версию снимка и непустой каталог.
6. Только после успеха останавливает старый редактор и запускает новый на постоянном порту. Затем повторяет проверку. Переключение сопровождается коротким перерывом в работе редактора.
7. При ошибке переключения возвращает предыдущий контейнер. Если новая версия не прошла первоначальную проверку, рабочий контейнер вообще не останавливается.

Контейнер `<name>-previous` остаётся остановленным для отката; проекты находятся в том же именованном volume. Скрипт никогда не удаляет volumes и отказывается заменять одноимённые контейнеры без своей метки управления. Это не откат содержимого базы: будущие изменения схемы должны сохранять совместимость с предыдущей версией приложения. Первичный перенос проектов из локальной SQLite или ранее созданного Compose-volume выполняется отдельно, до первого деплоя.

Если публикация игры не удалась, редактор не обновляется. Если игра опубликована, но деплой редактора не удался, workflow будет красным, предыдущий редактор останется доступен; повторите публикацию после исправления причины. Принудительная остановка runner/процесса может прервать автоматический откат; следующий деплой восстанавливает сохранённый предыдущий контейнер, если активного нет. Старые Docker-образы не очищаются глобальным prune.

`ci_build.sh` используется обоими workflow, `deploy.py` управляет переключением. В Docker предусмотрен `HEALTHCHECK` через встроенную команду `dotnet EconomyEditor.dll --healthcheck`; curl внутри образа не требуется.
