# Диздок: МОД-костюмы Innovation Station

Полная переработка МОД-сьютов «с нуля» по мотивам `/tg/station`, но с главным
дополнительным требованием: **бо́льшая часть системы должна быть переиспользована
будущим реворком мехов**. Поэтому проект делится на два слоя — универсальный
каркас «модульного шасси» и надстройка «костюм» поверх него.

Источники: `BandaStation-master/code/modules/mod/*` (форк /tg/station),
текущая Goob-реализация в `Content.Goobstation.Shared/Clothing/*`.

---

## 1. Философия и принципы

**МОД-костюм — это не «броня с кнопкой», а платформа, которую игрок собирает под себя.**

1. **Костюм = ядро + обшивка + модули.** Ни одна из трёх частей сама по себе не играет.
   Ядро даёт энергию, обшивка — внешний вид, броню и лимит сложности, модули — весь функционал.
2. **Функционал живёт в модулях, а не в прототипе костюма.** Два инженера с одинаковой
   обшивкой должны собираться по-разному. Если фича «вшита» в костюм — это ошибка дизайна.
3. **Бюджет сложности — главный источник решений.** Всё влезть не может никогда.
   Игрок выбирает между «фонарь + хранилище» и «джетпак».
4. **Три состояния, а не два.** Сложен → развёрнут → загерметизирован. Промежуточное
   состояние «развёрнут, но не запечатан» — это ключ к тому, чтобы костюм не был
   «просто скафандром»: в нём можно ходить без штрафов, но он не держит давление.
5. **Костюм — вещь, которую можно вскрыть.** Панель проводов, ID-замок, отсек с батареей,
   отвёртка и лом — всё это контент для взломщика ничуть не меньше, чем для владельца.
6. **Новый модуль — это YAML, а не C#.** Библиотека готовых поведений закрывает 80% идей.
   C# пишется только под действительно уникальную механику.

**Анти-цели:** костюм-«всё-в-одном» без выбора; модули, каждый из которых требует своей системы;
жёсткая привязка к слоту «спина» на уровне кода; невозможность переиспользовать код в мехах.

## 2. Что не так с текущей реализацией

Сейчас в билде две несвязанные ветки МОД-сьютов (Goob и EinsteinEngines) и обе —
не модульные системы, а набор захардкоженных костюмов:

| Проблема | Как сейчас |
|---|---|
| Нет модулей вообще | Весь функционал прибит к прототипу конкретного костюма (`ComponentToggler` с `PressureProtection` прямо в нагруднике) |
| Нет ядра и нет энергии как ресурса | `SealableClothingRequiresPower` — единственная связь с питанием, «есть заряд / нет заряда» |
| Нет UI | Есть только экшен «загерметизироваться» |
| Нет панели проводов и ID-замка | Отсутствуют |
| Нет бюджета сложности | Отсутствует |
| Нет сборки | `Construction`-граф собирает целиком готовый костюм фиксированной модели |
| Развёртывание частей — хак поверх `ToggleableClothing` | Апстримный компонент раздут Goob'ом (`ClothingPrototypes`, `EquippedPrefixes`, `ClothingUids`) — правки в апстримном файле, конфликты при синках |
| Тема/обшивка не существует как понятие | Каждый скин — отдельное дерево из 5 прототипов с копипастой брони |

Итог: чтобы добавить костюм, нужно скопировать ~250 строк YAML; чтобы добавить фичу — писать систему.
Это ровно то, что новая архитектура должна убрать.

## 3. Архитектура: два слоя

```
+-----------------------------------------------------------------+
|  Content.Shared/_IS14/Modular/       МОДУЛЬНОЕ ШАССИ            |
|  (переиспользуется мехами)                                      |
|                                                                 |
|   ModularChassisComponent   — хост модулей, бюджет сложности    |
|   ChassisModuleComponent    — предмет-модуль, тип, стоимость    |
|   ChassisPowerComponent     — абстракция «откуда заряд»         |
|   ModuleBehaviour*Component — библиотека готовых поведений      |
|   события установки/включения/использования                     |
|   BUI + окно со вкладками + радиальное меню                     |
+-----------------------------------------------------------------+
                 ^                              ^
                 |                              |
+----------------+--------------+  +------------+-------------------+
| Content.Shared/_IS14/Modsuit/ |  | Content.Shared/_IS14/Mech/     |
|  ModsuitControlComponent      |  |  (будущий реворк мехов)        |
|  ModsuitPartComponent         |  |  кабина, оборудование, ножницы |
|  ModCoreComponent             |  |  — те же модули, тот же UI     |
|  развёртывание / герметизация |  |                                |
|  скины, обшивка               |  |                                |
+-------------------------------+  +--------------------------------+
```

Правило разделения: **всё, что не знает слова «одежда», «слот инвентаря» и «носитель» —
живёт в `Modular/`.** Всё, что знает — в `Modsuit/`.

Проверка на переиспользуемость: если мех не сможет использовать компонент как есть —
компонент лежит не в том слое.

## 4. Структура сущностей

МОД-костюм — это **одна сущность-контроллер** (носится в слоте `back`), внутри которой лежит всё остальное.

```
ModsuitControl (сущность, слот back)
├── контейнер  "mod-parts"          — 4 части костюма, когда сложены
│     ├── ModsuitHelmet     (слот head)
│     ├── ModsuitChestplate (слот outerClothing)
│     ├── ModsuitGauntlets  (слот gloves)
│     └── ModsuitBoots      (слот shoes)
├── контейнер  "mod-modules"        — установленные модули
│     ├── ModuleFlashlight
│     ├── ModuleStorage
│     └── ...
├── ItemSlot   "mod-core"           — ядро (обязательно для работы)
│     └── ModCoreStandard
│           └── ItemSlot "cell_slot" — батарея (PowerCellSlot)
├── WiresPanel + Wires              — панель проводов
├── AccessReader                    — ID-замок
└── ActivatableUI                   — интерфейс костюма
```

Части — **настоящие сущности одежды**. При развёртывании они переезжают из контейнера
в слоты инвентаря носителя и получают `Unremoveable`, при сворачивании — обратно.
Это позволяет частям иметь собственную броню, собственные спрайты `equipped-*`,
собственный `Storage` (нагрудник) и собственные слои модульных оверлеев.

### Почему набор частей не фиксирован

`ModsuitControlComponent.Parts` — это словарь `SlotFlags → EntityUid`, а не четыре поля.
Это даёт бесплатно: костюмы из 2 частей (лёгкий «портативный» скафандр), костюмы с маской
вместо шлема, костюмы без перчаток. Модули объявляют требуемые слоты через тот же `SlotFlags`.

## 5. Три состояния костюма

```
   СЛОЖЕН                РАЗВЁРНУТ                ЗАПЕЧАТАН (активен)
 +----------+   deploy  +----------+  activate   +----------+
 | рюкзак   | --------> | надет    | ----------> | активен  |
 | на спине | <-------- | целиком  | <---------- |          |
 +----------+  retract  +----------+ deactivate  +----------+
```

| | Сложен | Развёрнут | Запечатан |
|---|---|---|---|
| Части в слотах | нет | да | да |
| Броня частей | нет | **да** | да |
| Держит давление / вакуум | нет | нет | **да** |
| Тепло/холодозащита | нет | нет | **да** |
| Скрывает волосы/лицо/маску | нет | нет | **да** |
| Замедление | нет | нет | **да** (по теме) |
| Расход энергии | нет | нет | **да** |
| Модули работают | нет | нет* | **да** |
| Можно снять костюм | да | нет (части надеты) | нет |

\* кроме модулей с флагом `AllowInactive`.

**Развёртывание** — мгновенное, по частям (радиальное меню) или всё разом.
**Герметизация** — последовательная, ~1 с на часть, с попапом и звуком на каждую
(«ботинки защёлкиваются», «нагрудник герметизируется», …). Прерывается движением/уроном.
Это ощутимая пауза перед выходом в космос — важный элемент напряжения, его нужно сохранить.

**Частичная герметизация возможна:** можно свернуть шлем на запечатанном костюме — он
расшивается отдельно, остальные части остаются запечатанными. Модули, требующие шлема,
при этом отключаются. Это то, что делает систему живой.

## 6. Ядро и энергия

### Модель

`ChassisPowerComponent` на шасси не знает, откуда берётся заряд. Он поднимает события:

```csharp
ChassisGetChargeEvent(out float Current, out float Max)
ChassisTryUseChargeEvent(float Amount, out bool Handled)
ChassisAddChargeEvent(float Amount)
```

Отвечает на них тот, кто может — обычно `ModCoreComponent` на ядре в слоте.
Мех подпишет на те же события свою батарею и получит весь UI зарядки бесплатно.

### Типы ядер

| Ядро | Источник заряда | Особенность |
|---|---|---|
| **Стандартное** | обычный power cell в своём `ItemSlot` | батарею можно менять и заряжать в зарядниках |
| **Плазменное** | сжигает листы плазмы | самозарядка, но нужен расходник; лаваленд-версия |
| **Реакторное** | встроенная батарея большой ёмкости | не меняется, заряжается только в зарядной станции |
| **Бесконечное** | — | админское / антаг-топ |

Ядро обязательно: без него костюм разворачивается, но не герметизируется и не даёт модулей.

### Числа (стартовая калибровка, тюнится)

Ёмкости батарей в билде: Small 360 Дж, Medium 720, High 1080, Hyper 1800.

| Параметр | Значение |
|---|---|
| Базовый расход запечатанного костюма | **0.5 Вт** |
| Стандартное ядро + Medium cell | 720 Дж → **24 мин** в вакууме без модулей |
| Стандартное ядро + Hyper cell | 1800 Дж → **60 мин** |
| Пассивный модуль | 0 Вт |
| Включаемый модуль (лёгкий: фонарь, визор) | 0.1–0.3 Вт |
| Включаемый модуль (тяжёлый: джетпак, магнитные ботинки) | 0.8–2 Вт |
| Разовое использование (дефибриллятор, инъектор) | 10–40 Дж за раз |
| Множитель расхода по теме | ×0.25 (гражданский) … ×2 (прототип) |

При нулевом заряде костюм принудительно расшивается (не мгновенно — с попапом-предупреждением
за ~10% заряда).

## 7. Модули

### 7.1 Четыре типа

| Тип | Поведение | Примеры |
|---|---|---|
| **Passive** | работает всегда, пока модуль установлен и части на месте | хранилище, защита от ЭМИ, антискольз, долгое падение |
| **Toggleable** | вкл/выкл, ест энергию пока включён | фонарь, визор, терморегулятор, магнитные ботинки, джетпак |
| **Usable** | разовое срабатывание + кулдаун | инъектор, диспенсер, «микроволновый луч» |
| **Active** | одновременно активен только один; даёт предмет в руки **или** особый клик по цели | дефибриллятор, дрель, гидрозахват, кинезис, медлуч |

### 7.2 Поля `ChassisModuleComponent`

```csharp
ModuleKind   Kind;              // Passive | Toggleable | Usable | Active
int          Complexity;        // цена в бюджете шасси
float        IdleDraw;          // Вт, пока установлен
float        ActiveDraw;        // Вт, пока включён
float        UseCost;           // Дж за срабатывание
TimeSpan     Cooldown;
bool         Removable = true;  // встроенные модули темы — false, Complexity = 0
List<SlotFlags> RequiredSlots;  // [HEAD, GLOVES|FEET] — «И» по элементам, «ИЛИ» внутри
ProtoId<TagPrototype>[] Conflicts;  // теги несовместимости (двусторонняя проверка)
ModuleAllowFlags Allow;         // Unworn | ChassisInactive | Incapacitated
```

`RequiredSlots` — точная копия удачной идеи /tg/: модуль дефибриллятора требует перчаток,
визор — шлема, джетпак — нагрудника. Если часть свёрнута или расшита — модуль автоматически
отключается и подсвечивается в UI как «недоступен».

Конфликты через **теги**, а не через типы: `Conflicts: [ModsuitVisor]` — все визоры
несовместимы друг с другом, но модуль ночного зрения (не-визор) с ними уживается.

### 7.3 Событийная модель

Модуль сам по себе ничего не делает — он рассылает события, на которые отвечают
компоненты-поведения, висящие на той же сущности модуля.

| Событие | Когда |
|---|---|
| `ModuleInstalledEvent` / `ModuleUninstalledEvent` | установка в шасси / изъятие |
| `ModuleEnabledEvent` / `ModuleDisabledEvent` | требования по частям выполнены / нарушены |
| `ModuleActivateAttemptEvent` | попытка включить (отменяемое) |
| `ModuleActivatedEvent` / `ModuleDeactivatedEvent` | включён / выключен |
| `ModuleUsedEvent(user, target?)` | разовое срабатывание |
| `ModuleGetUiDataEvent` | сбор кастомных данных для UI |
| `ModuleGetConfigEvent` / `ModuleConfigChangedEvent` | настройки модуля из UI |
| На шасси: `ChassisModulesChangedEvent`, `ChassisPowerChangedEvent`, `ChassisStateChangedEvent` | |

### 7.4 Библиотека поведений (главная инвестиция в гибкость)

Эти компоненты пишутся **один раз** и покрывают подавляющее большинство модулей.
После них новый модуль = один YAML-прототип.

| Компонент | Что делает | Покрывает модулей |
|---|---|---|
| `ModuleGrantComponentsComponent` | навешивает компоненты на цель (`Wearer` / `Chassis` / `Part`) пока модуль включён | ~40% всего: все визоры и HUD'ы, ночное зрение, защита от радиации, антискольз, терморегулятор, сварочная защита, стабилизатор плазмы, долгое падение |
| `ModuleActionComponent` | выдаёт носителю экшен | джетпак, магнитные ботинки, тросомёт |
| `ModuleItemComponent` | держит сущность-девайс, выдаёт её в руки при активации (`Active`) | дефибриллятор, анализатор здоровья, дрель, гидрозахват, магнит, сканер реагентов |
| `ModuleStorageComponent` | включает `Storage` заданного объёма на нагруднике | все хранилища, рудный мешок, кобура |
| `ModuleSpeedModifierComponent` | правит скорость носителя | «торсионная трещотка», компрессия пластин |
| `ModuleArmorModifierComponent` | добавляет коэффициенты брони частям | усилитель брони, компрессия пластин |
| `ModuleLightComponent` | `PointLight` на костюме + спрайтовый оверлей | фонарь, «фонарь тьмы» |
| `ModuleTargetedActionComponent` | клик по цели с кулдауном и радиусом (`Active` без предмета) | кинезис, медлуч, захват преступника |
| `ModuleWornOverlayComponent` | спрайтовый оверлей поверх части (состояния вкл/выкл/кулдаун) | визуал ~30 модулей |
| `ModuleAlertComponent` | алерт на HUD носителя | статус-ридаут, ДНК-замок |

Оставшиеся 20% (кинезис, физика джетпака, стелс) требуют своей системы — и это нормально.

## 8. Тема, обшивка, скин

Три разных понятия, которые важно не смешать:

- **Тема (theme)** — «инженерный», «военный», «гражданский». Задаёт статы: броня, лимит сложности,
  расход, замедление, набор встроенных модулей, разрешённое содержимое кармана нагрудника.
- **Обшивка (plating)** — предмет, который вставляется при сборке и определяет тему.
- **Скин (skin)** — вариант внешнего вида внутри темы. Меняется набором для перекраски.

В SS14 тема реализуется как **прототип-родитель**:
`ModsuitControlBase` → `ModsuitControlEngineering` → конкретные варианты.
Отдельного `ModThemePrototype` не заводим — иерархия прототипов уже даёт наследование статов,
а `ModsuitSkinComponent` со списком доступных скинов даёт перекраску.

```yaml
- type: ModsuitSkin
  current: engineering
  skins:
    engineering: { rsi: _IS14/Clothing/Modsuits/engineering.rsi }
```

## 9. Сборка и производство

Цепочка, повторяющая /tg/, но на `Construction`-графе SS14:

```
пустой корпус (ModsuitShell)
   + ядро                                        -> корпус с ядром
   + отвёртка                                    -> закреплено
   + шлем / нагрудник / перчатки / ботинки       -> полный набор
   + гаечный ключ                                -> скручено
   + отвёртка                                    -> готово к обшивке
   + обшивка (plating темы)                      -> ГОТОВЫЙ КОСТЮМ
```

- Заготовки частей и корпус печатаются в **экзосьют-фабрикаторе** (сталь).
- Обшивки — по темам, каждая за своим ресёрчем и своим набором материалов
  (инженерная — золото, атмос — титан, мед — серебро, СБ — плазма).
- Модули печатаются отдельно, каждый за своим узлом техвеба.
- Ядра: стандартное — базовый ресёрч; плазменное — через плазму/лаваленд; реакторное — поздний ресёрч.

Это делает МОД-костюм **проектом отдела РнД на раунд**, а не предметом из шкафчика.
Стартовые (в шкафчиках) — только гражданский и стандартный, без модулей.

## 10. Панель проводов, замок, взлом

Панель открывается **отвёрткой** только когда костюм не активен и не развёрнут.
С открытой панелью доступны: установка модуля (клик модулем), извлечение (лом),
смена ядра (гаечный ключ), провода (кусачки/мультитул), перепись доступа (ID-карта).

| Провод | Импульс | Перерезать | Починить |
|---|---|---|---|
| **Hack** | переключить ID-замок | стереть весь доступ | — |
| **Disable** | сбой на время | костюм неисправен: ×3 расход, модули случайно вырубаются | вернуть норму |
| **Shock** | шибает током на время | шибает постоянно | снять |
| **Interface** | сломать/починить UI | UI недоступен | вернуть |
| ×2 пустышки | — | — | — |

`WiresSystem` в SS14 серверная, поэтому действия проводов — `Content.Server/_IS14/Modsuit/Wires/`.

**ID-замок:** пока заперт — нельзя открыть панель, вытащить модули и (опционально) активировать.
Снимается ID-картой с нужным доступом, ЭМАГом или проводом Hack.

**EMP:** отключает активный модуль, наносит небольшой ожог носителю, с шансом временно
ломает интерфейс.

## 11. Интерфейс

`ActivatableUI` + `BoundUserInterface`. Окно — **общее для костюма и будущего меха**
(`ModularChassisWindow`), поэтому оперирует только понятиями шасси/модулей/заряда,
а «части костюма» приходят отдельной секцией через данные состояния.

По правилам проекта: вся вёрстка в `.xaml`, логика в `.xaml.cs` с `[GenerateTypedNameReferences]`,
корневой тег = тип класса.

**Вкладка «Статус»**
- Полоса заряда (цвет + текст «540 / 720 Дж (75%)»), имя ядра
- Полоса сложности `9 / 15`
- Имя и должность носителя (с ID)
- Кнопка «Активировать / Деактивировать»
- Ряд частей: иконка + название + кнопка развернуть/свернуть у каждой
- Индикаторы: замок, панель, неисправность, поломка интерфейса

**Вкладка «Модули»**
Список карточек. Каждая карточка:
- иконка модуля, название, описание
- бейдж типа (пассивный / включаемый / разовый / активный)
- строка «Сложность 3 · 0.2 Вт · 25 Дж/исп.»
- кнопка действия (включить/выключить/использовать/выбрать), заблокирована с причиной
  («нужен шлем», «нет заряда», «кулдаун 4 с» — с прогресс-баром кулдауна)
- кнопка «закрепить» — вынести модуль на панель экшенов
- блок настроек, если модуль их отдаёт

**Настройки модулей — универсальные дескрипторы** (прямое заимствование удачной идеи /tg/):

```csharp
enum ModuleConfigKind { Bool, Number, Color, Choice, Button }
record ModuleConfigEntry(string Key, string Label, ModuleConfigKind Kind, object Value, object[]? Choices);
```

Так модуль инъектора отдаёт выбор реагента, фонарь — цвет и радиус, а UI не знает про них ничего.

**Вкладка «Железо»**
- Слот ядра (можно вынуть при открытой панели)
- Слот батареи внутри ядра — **проброшен наверх**, чтобы игрок видел «отсек с батареей» костюма
- Состояние панели, список доступа замка

**Вне окна:**
- Экшены на панели: «Развернуть», «Активировать», «Модули» (радиалка), «Панель» (открыть UI)
- Радиальное меню модулей (`SimpleRadialMenu`) — быстрый выбор без открытия окна;
  подсветка выбранного/включённого, затемнение на кулдауне
- Закреплённые модули — отдельные экшены в панели
- Алерт заряда костюма на HUD (как у скафандров)

и `_EinsteinEngines/Clothing/NanoTrasen/Modsuits/*.rsi` — конвертация уже сделана, переиспользуем.

### Оверлеи модулей — техническое ограничение

`ClothingComponent.ClothingVisuals` помечен `[DataField]` **без** `[AutoNetworkedField]` —
изменения на сервере до клиента не доедут. Значит оверлеи модулей делаются **клиентской системой**:

`Content.Client/_IS14/Modsuit/ModsuitVisualsSystem` читает сетевое состояние
`ChassisModuleComponent` (включён / на кулдауне / активен) и вставляет дополнительные
слои в спрайт носителя при `EquipmentVisualsUpdatedEvent` соответствующей части.
`ModuleWornOverlayComponent` описывает: RSI, состояния для трёх режимов, целевой слот,
нужна ли маска по силуэту части, красить ли в цвет костюма.

Это единственное место, где потребуется аккуратная работа с `ClientClothingSystem` —
заложен отдельный спайк в фазе 6.

### Покраска

Набор для перекраски (`ModsuitPaintKit`) — меняет `color` всех частей.
Аппликатор скина — меняет `ModsuitSkinComponent.current`.

## 13. Что именно переиспользуют мехи

Явный чек-лист, по которому проверяется правильность разделения:

| Отдаём мехам как есть | Не отдаём |
|---|---|
| `ChassisModuleComponent` + все `ModuleBehaviour*` | развёртывание частей |
| Бюджет сложности и проверки совместимости | герметизация |
| `ChassisPowerComponent` и события заряда | скины/обшивка одежды |
| Библиотека поведений (grant/action/item/storage/light/targeted) | оверлеи на носителе |
| `ModularChassisWindow` + BUI + дескрипторы настроек | ID-замок в текущем виде (мех даст свой) |
| Радиальное меню модулей | |
| Установка/извлечение модулей инструментами | |

Практически: **оборудование меха = модуль типа `Active` с `ModuleItemComponent`.**
Дрель меха и дрель костюма — один прототип с разной сложностью.

### Важно про лицензию

Спрайты `/tg/station` и BandaStation распространяются под **CC-BY-SA-3.0**, а не под AGPL.
При конвертации в каждый `meta.json` обязательно:

```json
"license": "CC-BY-SA-3.0",
"copyright": "Taken from tgstation at commit <hash>, https://github.com/tgstation/tgstation"
```

Иначе `reuse-updater.yml` и ревью зарежут PR.

### Конвертацию можно не делать вручную

DMI — это обычный PNG со спрайтшитом и метаданными в `zTXt`-чанке `Description`
(размер клетки, список состояний, число направлений, кадры, задержки). Разбор и
нарезка в RSI автоматизируются скриптом — уже проверено на этих файлах.
Ручная работа останется только там, где спрайт нужно доработать под наши пропорции.

### Целостность обшивки

Каждая часть носит собственный запас прочности: шлем 250, корпус 300, перчатки 200,
ботинки 200. Урон, попавший в тело под частью, снимает её целостность.

| Часть | Прикрывает |
|---|---|
| Шлем | `Head` |
| Корпус | `Chest`, `Groin` |
| Перчатки | `FullArms` (руки и кисти) |
| Ботинки | `FullLegs` (ноги и стопы) |

Подписка идёт на `InventoryRelayedEvent<DamageModifyEvent>`: удар по мобу ретранслируется
на всё надетое, а `TargetPart` в событии говорит, куда именно пришлось. Считается
`OriginalDamage`, а не текущий `Damage` — обшивка изнашивается от того, что в неё
попало, а не от остатка, который её собственная броня пропустила. Иначе чем лучше
костюм, тем дольше он живёт, что задом наперёд.

`ModsuitPartComponent.DamageMultipliers` умножает урон по типам; по умолчанию
`Ion: 2` — ионное оружие направляют ровно в такие штуки.

Порогов два, и они делают разные вещи.

| Порог | Поле | Что происходит |
|---|---|---|
| 66% | `moduleThreshold` | часть перестаёт отдавать свой `SlotFlag` в `ChassisGetAvailableSlotsEvent`, все модули на этом слоте гаснут через штатный `MissingParts`. Герметичность сохраняется |
| 33% | `unsealThreshold` | часть срывает герметизацию сама и отказывается запечатываться, пока её не починят. Остальной костюм закрывается вокруг неё |

Первый порог — это «модули отвалились, но ты ещё жив». Второй — «беги к шлюзу».
Потерять одну часть при этом можно: `TryToggleSeal` пропускает вскрытые части вместо
того, чтобы упираться, так что костюм закрывается всем, что ещё цело.

### Ремонт

Тип поломки не бросается кубиком, а выводится из того, чем били. Каждая часть копит
две суммы: `structuralWear` (тупой урон, прокол, рез) и `electricalWear` (всё
остальное — лазеры, ион, ток). Что перевесило, того и требует часть:

| Поломка | Чем чинится | Что тратится |
|---|---|---|
| `Structural` — погнутая обшивка | сварка (`Welding`) | топливо горелки, `repairFuel` |
| `Electrical` — выгоревшая проводка | моток кабеля (тег `CableCoil`) | 1 кабель за подход |

Работают по самой части, а не по блоку управления: часть разворачивают, а потом
кликают по её слоту экипировки инструментом в руке. Клик по занятому слоту предметом
в руке — это уже штатное `InteractUsing` по надетой вещи (`InventorySystem.OnUseSlot`),
так что погнутую перчатку чинят на перчатке, а не машут горелкой над ранцем.

Следствие: обслуживают свой костюм, разворачивая часть за частью. Костюм, лежащий на
полу, обслужить нельзя — его части сложены внутрь и до них не дотянуться. Чужой костюм
тоже не починить: меню обыска не пробрасывает `InteractUsing` на надетое.

Один подход возвращает `repairFraction` (25%) от максимума и списывает столько же
накопленного износа своего типа, так что костюм, который и били, и жгли, требует
обоих инструментов по очереди. Не тот инструмент — попап говорит, какой нужен.

Мультитул сюда специально не взят: на костюме есть `WiresPanel`, и `Pulsing` по нему
уже открывает меню проводов.

### Управление и хоткеи

| Ввод | Действие |
|---|---|
| `E` | открыть отсеки модуля хранения (`StorageComponent.OpenOnActivate`) |
| `Alt+E`, альт-клик | открыть панель костюма |
| лом по открытой панели | вынуть ядро |
| сварка / кабель по слоту развёрнутой части | ремонт этой части |
| умное экипирование по спине | отсеки хранения (ядро оно больше не трогает) |

`ActivatableUI` на костюме объявлен как `verbOnly: true` + `altVerb: true`:
`verbOnly` снимает панель с обычного `ActivateInWorldEvent`, освобождая `E`,
а `altVerb` (губ) переносит вербу в альтернативный список, куда бьют и `Alt+E`,
и альт-клик. Ядро вынимается **только ломом**. `ModCoreSystem` отменяет `ItemSlotEjectAttemptEvent`
для слота `mod-core`, когда извлечение затеял человек, и это разом закрывает вербу
«извлечь» в ПКМ-меню, кнопку слота и умное экипирование. Лом идёт мимо: он вынимает
ядро прямым `Container.Remove`, не проходя через `CanEject`. Отмена не трогает случаи
с `user == null` — разрушенный костюм по-прежнему отдаёт ядро наружу.

Побочный и нужный эффект: умное экипирование по спине больше не выдёргивает ядро.
`SmartEquipSystem` сначала пробует слоты предметов, но `TryEjectToHands` теперь
возвращает false, и обработчик проваливается дальше — в ветку хранилища, то есть
костюм с модулем хранения ведёт себя как обычный рюкзак.

### Лом достаёт только ядро

Лом на открытой панели поднимает `ChassisPryEvent`; отвечает `ModCoreSystem` на слое
костюма и отдаёт ядро в руки. Модулей лом больше не касается — у каждого есть кнопка
«Извлечь» в интерфейсе, где состояние панели и так на экране. Событие сначала
поднимается с `DryRun`, чтобы инструмент отказал сразу, а не после двух секунд.

### Как устроен интерфейс

Окно рисует себя из собственной палитры (`Content.Client/_IS14/Modular/Controls/`),
а не из станционного стайлшита — так МОД выглядит как приборка на спине и при этом
не требует правок в upstream-стилях.

- `ChassisStyle` — палитра и фабрика панелей/чипов.
- `ChassisButton` — кнопка на `StyleBoxOverride`, с состоянием «залипла».
- `BatteryGauge` — заряд как настоящая ячейка: корпус, клемма, 12 сегментов, мигание на нуле.
- `ComplexityBar` — бюджет сложности насечками, чтобы считать оставшееся место глазами.

#### Где переносится текст, а где нет

Описание модуля раскрывается по нажатию на карточку и должно переноситься по строкам.
Два места, где это ломается, и оба неочевидны:

1. `ScrollContainer` с включённой горизонтальной прокруткой (а она включена по умолчанию)
   меряет детей с бесконечной шириной. Текст, которому не сказали, сколько у него места,
   не переносится никогда. Отсюда `HScrollEnabled="False"` на бэе модулей.
2. Горизонтальный `BoxContainer` меряет детей по очереди, вычитая уже занятое. Описание,
   лежащее в одной строке с кнопками, получит при замере и их ширину тоже — и уедет под
   них при отрисовке, потому что рисуется по замеру, а не по разметке. Поэтому карточка —
   колонка: строка «иконка / название / кнопки», а описание отдельной строкой под ней во
   всю ширину.

Слева бумажная кукла: голова сверху, руки и корпус в ряд, ботинки снизу, справа от
корпуса — сам блок управления. Нажатие на плитку раскрывает под куклой меню этой части
(развернуть/сложить, загерметизировать), нажатие на блок управления — состояние железа.

### Осознанные отклонения от плана

1. **Производство — рецепты экзокостюмного фабрикатора, а не граф сборки.**
   Рецепты модулей и ядра при переходе на граф переносятся без изменений.
2. **Мезонного визора нет** — в билде отсутствует компонент мезонного зрения.
   Вместо него модуль ночного визора на `NightVision` из Goob.
3. **Джетпак и стабилизатор плазмы не сделаны.** `JetpackComponent` требует газового
   баллона, а `IgniteFromGasImmunityComponent` срабатывает только по событию надевания —
   оба несовместимы с выдачей компонента «на лету». Нужен свой C#, вынесено в бэклог.

### Ограничение библиотеки поведений

`ModuleGrantComponents` годится только для компонентов, которые работают сразу после
навешивания: маркеры и статы, читаемые через inventory relay или прямой подпиской
(`NoSlip`, `EyeProtection`, `NightVision`, HUD-иконки, `EmpResistance`,
`RadiationProtection`, `TemperatureProtection`). Компоненты, которым нужен собственный
жизненный цикл предмета — событие надевания, свой контейнер, своя цель клика — требуют
отдельного поведения. Это граница, а не баг: проверять её надо до того, как модуль попал
в прототип.

### Расхождения с диздоком, найденные при реализации

- `ClientClothingSystem` строит надетые состояния как `{префикс}-equipped-{слот}`,
  поэтому запечатанные спрайты названы `sealed-equipped-HELMET`.
- Движок допускает **ровно один обработчик на пару (компонент, событие)** во всей игре.
  Из-за этого смена носителя раздаётся модулям ретрансляцией (`ModuleUserChangedEvent`),
  а визуал контроллера дёргается из уже существующего обработчика состояния шасси.
- `StorageComponent` сеточный (`List<Box2i>`); `MaxItemSize` и `MaskPath` у `PointLight`
  закрыты `[Access]` и задаются только в прототипе.
- `ClothingComponent.ClothingVisuals` не сетевой, поэтому оверлеи модулей рисует
  клиентская система через `GetEquipmentVisualsEvent`, а не сервер.

### Ключи проводов живут в Shared

Панель проводов кладёт свои `StatusKey` внутрь `WiresBoundUserInterfaceState`, а тот
уходит в сетевое состояние. Ключ, объявленный в `Content.Server`, компилируется,
проходит линтер и стартует без единой жалобы — а потом валит сервер посреди тика,
как только кто-то открывает панель: PVS не может сериализовать тип, о котором клиент
никогда не слышал (`KeyNotFoundException: Type not found`).

Поэтому `ModsuitWireKey` лежит в `Content.Shared/_IS14/Modsuit/` с
`[Serializable, NetSerializable]`, как и все ключи проводов апстрима. Тест
`WireKeysAreNetSerialisable` спрашивает у `IRobustSerializer`, знает ли он этот тип, —
это ловушка, которую не видят ни компилятор, ни линтер.

### Модуль как окно

`ModuleInterface` — второй способ «использовать» модуль после выдачи предмета.
Модуль объявляет свой `UserInterface`, поведение указывает ключ, и дальше:

- включение модуля открывает окно оператору шасси;
- закрытие окна выключает модуль, а с ним и `activeDraw`;
- снятие модуля или потеря нужной части закрывают окно.

Первым его получил навигационный модуль: координаты видно всегда (`HandheldGPS`
пассивно на шасси), а по кнопке разворачивается карта станции. Сканеры масс и монитор
экипажа встанут туда же — им нужен только свой `UserInterface` на прототипе.

### Почему устройство метится, а не модуль

Модуль вида «выдать инструмент» не может списывать заряд при активации: бур достают
один раз, а стоит работа. Поэтому `ChassisDevicePowerSystem` подписан на само
устройство — `AttemptMeleeEvent` для замаха и `AfterInteractEvent` для дефибриллятора и
конструктора, — берёт `useCost` за действие и отменяет действие, если костюму платить
нечем. Подписка на `AfterInteractEvent` идёт `before: [typeof(RCDSystem)]`, чтобы
неоплаченная постройка не начиналась вовсе.

### Настройки модуля в интерфейсе

`ModuleGetConfigEvent` существовал с самого начала, но окно его не рисовало. Теперь

### Атмосферика

Модуль вешает `GasTank` на шасси. Из этого само собой следует всё остальное: внутреннее
дыхание подключается к костюму как к баллону, а `JetpackSystem` требует `GasTank` на той
же сущности, что и `Jetpack`, — поэтому джетпак-модуль работает только вместе с
атмосферным. Компрессор живёт на сервере (атмосфера есть только там), тикает раз в
секунду, тянет выбранные газы из тайла до `targetPressure` 1013.25 кПа и платит зарядом
за реально перенесённые моли. На тайле всегда остаётся резерв — костюм, способный
откачать комнату, был бы оружием, а не модулем.

Выбор газов — обычные настройки модуля, то есть та же раскрытая карточка.

### Плазменное ядро

`ModCoreFuel` принимает стеки по типу, а не по тегу: `Plasma` за 400 Дж лист,
`PlasmaOre` за 150 Дж кусок. Кормить можно и само ядро в руке, и надетый костюм —
второе важнее, иначе ядро пришлось бы выковыривать ломом каждый раз.

### Два хранилища на одном костюме

У сущности может быть только один `StorageComponent`, поэтому второй модуль хранения
на шасси не помещается в принципе. Отсюда `ModuleStorage.onChassis`: общие отсеки
по-прежнему висят на костюме (их открывает `E`, они переживают замену модуля на
больший), а специализированный мешок несёт сам модуль. Такой мешок уходит вместе с
модулем со всем содержимым — это не потеря, а логика: вынули мешок — вынули с рудой.

Размер предмета у такого модуля объявлен `Large`: хранилище без явного предела берёт
предметы на размер меньше себя, и маленький модуль отказал бы обычному куску руды.

Тег у рудного мешка свой — `IS14ModsuitOreStorage`. С обычными отсеками он уживается,
со следующим рудным мешком (бэ-эс версией) — нет.

### Новые модули этого круга

Атмосферика малая и большая, джетпак, рудный мешок, компактность (даёт костюму слот
пояса, конфликтует с отсеками), тэ-скан, перцовый отпор. Перцовый отпор ставит метку на
носителя и отвечает на `AttackedEvent` и `DisarmedEvent` — оба поднимаются на человеке,
а толчок до ретрансляции по надетому не доходит вовсе.

### Правки после двенадцатого игрового теста

**Баллон живёт по установке, а не по герметичности.** Раньше модуль атмосферики
следовал `Enabled`, то есть запечатанному нагруднику, и расшитый костюм терял
`GasTankComponent` вместе со всем газом — интерфейс честно писал «баллона нет».
Отсюда третий режим жизни поведения, `ModuleBehaviourSystem.FollowsInstallation`:
начинается по `ModuleInstalledEvent`, кончается по `ModuleUninstalledEvent`, и
включение-выключение шасси его не касается. Пока что он нужен ровно одному поведению,
и это правильное соотношение — почти всё остальное обязано гаснуть вместе с костюмом.

Герметичность теперь управляет двумя вещами вместо одной:

- **запечатанный нагрудник** — компрессор (это по-прежнему `Enabled` модуля через
  `requiredSlots: [OUTERCLOTHING]`, никакого нового кода);
- **герметичность целиком** — дыхание. `IsFullySealed` строже, чем `IsSealed`:
  требует, чтобы все четыре части были и развёрнуты, и запечатаны, и не вскрыты.
  Шлем при этом получает `BreathToolComponent`, и дальше работает штатная механика
  внутреннего дыхания. Компонент сам подключается на инициализации (правка Goob в
  `LungSystem`) и сам отключает внутренние при выключении, так что снимать его
  достаточно через `RemComp`.

Газ из баллона при снятии модуля не исчезает: `Stop` кладёт смесь в
`ModuleGasTankComponent.Stored`, `Start` возвращает. Модуль — это и есть бутылка,
переставить её в другой костюм должно быть переносом воздуха, а не сливом на пол.

### Манометр стал приборной панелью

Компрессор и клапан переехали из настроек модуля на сам манометр: давление, на которое
они влияют, там уже нарисовано. Никакого нового канала сообщений при этом не появилось —
кнопки шлют тот же `ChassisConfigureModuleMessage` с ключами `pump` и `valve`, что и
карточка модуля, просто состояние знает `TankModule` в стейте. Выбор газов остался в
настройках модуля: это настройка, а не рычаг.

Рядом с давлением — температура в цельсиях и состав: три крупнейшие доли по имени и
проценту, остальное одной строкой «прочее». Имя и цвет газа клиент берёт из
`GasPrototype`, поэтому список работает для любого газа, а не только для тех трёх,
что умеет фильтровать модуль.

### Сложность переехала к модулям

Полоса бюджета стояла под батареей, хотя тратят его модули. Теперь она в шапке отсека
модулей, пустые ячейки рисуются контуром, а не серой заливкой: пустая розетка читается
как «влезет ещё один», серый прямоугольник — как «занято непонятно чем».

Единицы измерения на карточках стали значками: сложность — иконка связанных узлов
(`_IS14/Interface/VerbIcons/complexity.png`), потребление — молния. Подпись вида
«0.2 Вт покоя» превращала карточку в предложение; отличие покоя от работы теперь несёт
цвет и подсказка. Тип модуля уехал из верхнего правого угла в нижний правый, к цифрам:
имя ищут, тип — подтверждают.

### Рудный мешок стал магнитом

Мешок теперь `Toggleable`: включённый тянет руду с пола на ходу. Своё поведение
(`ModuleMagnet`), а не апстримный `MagnetPickup` — тот заведён на `ItemToggle` и на
отметку времени, поставленную в `MapInit`, чего у выданного посреди раунда модуля нет.
Заодно свой код позволил брать плату за подъём: пустой проход бесплатен, удачный стоит
заряда. Тянет он ровно то, что примет сам мешок — белый список у хранилища один.

Кнопка «открыть» у такого мешка не работала по простой причине: сетка живёт на модуле,
значит и окно должно открываться на модуле, а `UserInterface` с ключом хранилища был
только у костюма. Теперь запись есть у модуля, а сама кнопка переехала в настройки
(`ModuleStorage` отдаёт `open` как `Button`) — у включаемого модуля переключатель занят
магнитом.

### Правки после тринадцатого игрового теста

**Альт-клик снова открывает панель.** Выданный костюму `GasTankComponent` вешает на него
свою альтернативную вербу «открыть клапан», а альт-клик выполняет верб с наибольшим
приоритетом — при равных нулях побеждал алфавит. У `ActivatableUIComponent` приоритета
не было вовсе, поэтому он появился: `verbPriority` (правка в маркерах, две строки в
системе и поле в компоненте), у костюма выставлен в 10. Это лечит класс проблемы, а не
один случай: всё, что ещё повесит альт-вербу на костюм, теперь проигрывает панели.

**Клапан и компрессор перестали спорить.** Открытие клапана глушит компрессор, включение
компрессора закрывает клапан — качать в открытую бутылку означает качать в комнату.
Плюс серверный компрессор сам отказывается работать при открытом клапане: клапан можно
дёрнуть вербой мимо панели, и об этом решении панель бы не узнала.

**Энергоблок стал вертикальным**, показания под ячейкой, а не сбоку — батарея высокая,
и цифры читаются под ней так же, как на самой ячейке. Освободившаяся ширина ушла
манометру.

**Строка герметичности.** Вместо объяснения «компрессору нужен запечатанный нагрудник»
в панели баллона стоит статус «Герметичность среды» с галочкой или крестиком: это
предусловие и для компрессора, и для внутреннего дыхания, поэтому у него своя строка,
а не повторение внутри каждого сообщения, которое от него зависит. Само объяснение
осталось подсказкой.

### Установленный модуль доступен через панель

Окно хранилища рудного мешка роняло сервер ассертом в `SharedInteractionSystem`.
Причина не в хранилище: у интерфейса есть радиус взаимодействия, и он проверяется не
только по расстоянию, но и через `IsAccessible`. Модуль лежит в закрытом контейнере
внутри костюма, поэтому обычные правила доступности говорят «дотянуться нельзя» — и это
верно про руки, но неверно про панель, через которую вообще всё это нажимается.
Интерфейс, открытый на недостижимой сущности, закрывается на следующем кадре, о чём
движок и предупреждает ассертом.

Лечится штатной точкой расширения: `ChassisModuleComponent` отвечает на
`AccessibleOverrideEvent` и одалживает ответ у шасси — кто дотянулся до костюма, тот
дотянулся и до того, что в него вкручено. Тот же ответ используется при периодической
проверке радиуса, так что окно больше и не закрывается само.

### Газ носит с собой тепло, а состояние окна строит только сервер

Две мелочи из одного корня — из того, что смесь газа networked-полем не является.

**Компрессор набивал баллон холодом.** `AdjustMoles` переносит моли, но не теплоту:
свежая `GasMixture` начинается с 2.7 K, и сколько бы воздуха из комнаты в неё ни
переложили, она такой и оставалась. Теперь компрессор собирает добычу в отдельную смесь
с температурой окружения и вливает её через `AtmosphereSystem.Merge`, который смешивает
температуры по теплоёмкостям. Заодно поменялся порядок: сначала плата, потом передача —
если заряда не хватило, воздух возвращается в комнату целиком, а не выкорчёвывается
обратно из уже перемешанной смеси. И предел набора считается не по «пока давление
меньше целевого» на каждом шаге, а один раз, по свободному объёму при температуре
приходящего газа.

**Давление мигало нулём при герметизации.** `UpdateUi` — общий код, и клиент во время
предсказания честно собирал состояние из своих компонентов и пушил его себе же.
`GasTankComponent.Air` не сетевое поле, у клиента оно пустое, отсюда «0 кПа» на кадр
до следующего серверного пуша. Состояние этого окна серверное по своей природе, поэтому
`UpdateUi` теперь на клиенте выходит сразу.

### Дыхание и джетпак: железо без переключателя

Обе поломки одной природы. Компонент, выданный посреди раунда, не проходит через
события надевания и инициализации карты — а именно они у апстрима раздают переключатели.

**Дыхание.** Костюм всё делал правильно: при полной герметичности шлем становится
`BreathTool`, баллон на спине находится штатным `FindBestGasTank`. Не хватало двух вещей.
Первая — `UseDelay` с записью `gasTank`: `ConnectToInternals` дёргает эту задержку и без
неё молча возвращает false, так что не работала и стандартная тревога-переключатель.
Вторая — `outputPressure`: у компонента по умолчанию целая атмосфера, а дыхательные
баллоны отдают 21.3 кПа, иначе костюм уходит в лёгкие в несколько раз быстрее, чем нужно.

Плюс кнопка «Дышать из баллона» рядом с манометром. Тревога в углу HUD работает и так,
но костюм, который становится дыхательным аппаратом только при всех запечатанных частях,
угадыванием не находится.

**Джетпак.** Выдавался `ModuleGrantComponents`, то есть появлялся `JetpackComponent` — и
всё. Включает джетпак `SetEnabled`, который вызывается из хотбар-действия, а действие
раздаётся по `GetItemActionsEvent` при надевании предмета. Компоненту, появившемуся
после надевания, его никто не выдаёт: железо стояло, тяги не было. Теперь у модуля своё
поведение, и его собственный переключатель и есть переключатель джетпака. Расход снижен
с движкового умолчания 0.012 до 0.0015 моль за импульс — бутылка костюма вчетверо меньше
настоящего ранца.

Отказ включиться видит только сервер (только он знает, сколько газа в баллоне), поэтому
пустой баллон отвечает всплывающей подсказкой, а не мёртвым тумблером.

### Джетпак: тумблер взводит, невесомость стреляет

Ручной джетпак зажигают и гасят вручную, и зажжённый на полу он ставит носителю
`BodyStatus.InAir` — отсюда и потеря управления при ходьбе. Модулю так вести себя нельзя:
его тумблер лежит в панели, и открывать панель по дороге из шлюза никто не станет.

Поэтому тумблер модуля теперь только **взводит** двигатели, а зажигает их невесомость.
На носителя вешается маркер `ChassisJetpackUser`, который слушает
`WeightlessnessChangedEvent`: шагнул за борт — включилось, вернулся на палубу —
выключилось, положение тумблера при этом не трогается. Снимать тягу нужно с того, на ком
она была заведена (`JetpackComponent.JetpackUser`), а не с текущего носителя костюма —
иначе передача костюма оставляет летать предыдущего.

### Ядро в панели: батарея и бункер

**Извлечение батареи.** Кнопка под показаниями энергоблока, по тому же правилу, что и
извлечение модуля: нужна открытая панель. Само ядро по-прежнему достаётся только ломом.

**Бункер вместо встроенной сетки.** Полноценная сетка инвентаря внутри окна МОДа
означала бы вытащить `StorageContainer` из клиентского контроллера хранилищ вместе с
его драг-н-дропом и предположением «окно хранилища одно» — несоразмерно много хрупкого
клиентского кода ради одной панели. Вместо этого у плазменного ядра собственное
хранилище 8×2, которое открывается кнопкой из окна МОДа: то же перетаскивание, тот же
штатный контрол, отдельное окно. Ядро сжигает содержимое само, по мере надобности,
раз в секунду и только на сервере — клиент, предсказывающий сжигание чужого топлива,
предсказывал бы его удаление.

Что влезет в бункер, решает та же таблица топлива, по которой ядро и заряжается:
второго списка нет, и научившееся новому топливу ядро примет его в том же движении.

**Предел размера предмета** у выданного на ходу хранилища приходится задавать явно —
без него он выводится из размера самой сущности, а ядро и модуль маленькие. Для этого в
`SharedStorageSystem` добавлен `SetMaxItemSize` (поле закрыто анализатором доступа);
рудный мешок с этого перешёл с раздувания собственного размера предмета на честный
`maxItemSize`.

**Обновление показаний.** Топливо пишется прямо в батарею ядра, мимо энергосистемы
шасси, поэтому панель не узнавала о нём до следующего события. Появился
`ChassisPowerSystem.NotifyChargeChanged` — заправка дёргает его и панель обновляется.

### «Нет ядра» и «нет батареи» — разные вещи

С точки зрения энергосистемы пустое гнездо и ядро с вынутой ячейкой выглядят одинаково:
заряд ноль, максимум ноль. Делать с ними надо разное, поэтому сообщение у них теперь
тоже разное, а панель показывает ровно одну из двух кнопок — ту сторону, в которую слот
сейчас может поехать: «Извлечь батарею» или «Вставить батарею» (из руки). Обе по правилу
открытой панели, как и извлечение модуля. Извлечение кладёт ячейку в руку, а не под ноги.

### Замок и саботаж сообщают о себе

`SharedModsuitLockSystem` не может дёрнуть панель напрямую: система костюма уже зависит
от него, обратная зависимость замкнула бы круг. Поэтому появился
`ModsuitSecurityChangedEvent` — одно событие на весь набор (замок, стёртый доступ,
сломанный интерфейс, сбой, электрификация), а не по одному на каждый переключатель.
Всё, что оно покрывает, видно только через панель, а панель всё равно перерисовывается
целиком.

## 18. Как достать человека из МОДа

До этого раздела костюм был неприступен: развёрнутые части неснимаемы, сам костюм не
снимается, пока хоть одна развёрнута, а надетый на чужой спине костюм физически нельзя
кликнуть — клик попадает в тело. У СБ не было ни одного хода. Здесь их пять, и все они
требуют, чтобы носитель был обездвижен, а не избит.

### Досягаемость

На носителя вешается `ModsuitWearerComponent`. Инструмент или карта, применённые к
человеку, пересылаются костюму — и дальше работают ровно те взаимодействия, которые у
отвёртки, мультитула, лома и карты уже есть с МОДом, лежащим на столе. Плюс костюм
считается достижимым (`AccessibleOverrideEvent`), иначе ни do-after панели, ни окно
проводов не откроются: надетая вещь лежит в чужом инвентаре, куда обычные правила
доступа не пускают.

И то и другое — только пока носитель **обездвижен**: в наручниках или не способен
действовать (оглушён, крит, мёртв). Намеренно не «ранен»: чтобы вытащить человека из
МОДа, его нужно скрутить, а не бить.

Читать панель костюма чужому по-прежнему нельзя (`ActivatableUIOpenAttemptEvent`) —
иначе всё остальное теряет смысл: нажал «сложить всё» и готово.

### Расшитую часть можно снять

`Unremoveable` теперь навешивается герметизацией, а не развёртыванием. Закрытая часть
держится на теле, открытая — снимается в меню обыска.

Снятая часть уходит **в костюм, а не в руки** обыскивающему: костюм ей владеет, а нужен
обыскивающему человек внутри. Иначе `Parts` ссылался бы на плитку, живущую где-то в мире,
и костюм становился бы неремонтопригодным. Для этого в `SharedStrippableSystem` появился
маркированный хук `StrippedItemRemovedEvent` — до снятия, а не после: костюм сам двигает
часть, и наполовину выполненный unequip под ним оставил бы плитку на полу.

Сам носитель стянуть с себя часть руками не может — у него для этого есть кнопка
складывания, а руками он бы рассыпал костюм по полу.

### Пять способов открыть

1. **Обесточить.** Лом в открытую панель достаёт ядро, костюм расшивается сам, части
   снимаются по одной. Ненасильственно, надёжно, ничего не ломает. Костюм при этом не
   складывается сам — снимать всё равно придётся руками.
2. **Провод аварийного сброса.** Импульс — костюм отпускает носителя целиком.
   Перерезанный — сброс не работает больше никогда, и тот, кто ждёт ареста в МОДе,
   перережет его заранее. Раскладка проводов случайная: нужен мультитул и готовность
   ошибиться.
3. **Карта доступа по открытой панели.** Не переключение замка, а override: департамент
   забирает своё железо у того, кто в нём стоит. Костюм СБ открывается картой СБ,
   краденый синдикатский — ничем.
4. **Резак.** Сварка по надетой плитке, урон идёт только плитке. Целится по кукле
   прицеливания: режется та часть, которая закрывает выбранную зону. Ниже 33% часть
   расшивается сама и снимается. Долго, шумно и стоит департаменту нагрудника — зато
   заключённого при этом никто не трогает.
5. **Подождать.** Запечатанный костюм ест заряд. Камера и время работают сами.

### Контригра владельца

Модуль ЕМП-щита, перерезанный заранее провод сброса, стёртый список доступа (тем же
проводом — тогда карта не поможет), заряженное ядро и, главное, не попадаться
обездвиженным. Ни один из пяти способов не работает на человеке, стоящем на ногах.
